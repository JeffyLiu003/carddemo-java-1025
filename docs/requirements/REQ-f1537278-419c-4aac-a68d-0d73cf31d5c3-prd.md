## 1. Background and goals

### 1.1 Background
Platinum card customers are the target segment of an acquisition/retention campaign. The bank wants to add a spending incentive: an extra 0.5% cashback on Platinum card spending for three months.

### 1.2 Goals
| ID | Goal | Measure |
|---|---|---|
| G-1 | Give Platinum customers an additional 0.5% cashback on qualifying spending | Cashback credited = 0.5% × qualifying amount, subject to rules in §5 |
| G-2 | Run for three months | All qualifying spending posted inside the confirmed campaign window (§5 BR-002) |
| G-3 | No manual work per customer | Cashback evaluated and credited automatically after posting; no manual batch |

### 1.3 Glossary
- **Qualifying spending** — a card purchase that satisfies product, window, amount and exclusion rules. **[Open]** exact definition (OI-04).
- **Additional cashback** — 0.5% on top of whatever cashback the customer already receives. **[Open]** whether "additional" stacks with the existing campaign (OI-03).
- **reward_grant / account credit** — existing marketing and account records used to pay cashback (see §7).

## 2. User roles and permissions

| Role | Responsibility | Permission |
|---|---|---|
| Platinum card customer | Use the card, view earned cashback | Own rewards only |
| Marketing operator (`A`) | Create/activate/pause/end the campaign, view performance | Existing admin menu |
| Card operations / support | Investigate missing cashback, trigger retry of PENDING rewards | Retry endpoint |
| Finance/reconciliation | Verify credited amounts and budget usage | Read-only reporting |

Existing POC constraint: services are loopback-only and do not enforce per-endpoint authorization (ADR-007); this is a known gap, not a target state.

## 3. Scope

### 3.1 In scope
- A three-month Platinum-card cashback scheme at an extra 0.5% on qualifying spending.
- Cashback evaluation triggered after transaction posting, credited to the card account.
- Idempotency, retry of failed credits, and operator visibility of campaign performance.
- Customer view of granted cashback.

### 3.2 Out of scope (preliminary, to confirm)
- Any change to interest, statements, minimum payment or credit limits.
- Points/loyalty currency, tier upgrades, A/B testing.
- Gold/standard products (they must not receive this cashback).
- New messaging middleware (baseline has none; ADR-009 Option B is a later evolution).

### 3.3 Assumptions and dependencies
- A-1: The existing marketing campaign capability (`docs/design/17-premium-cashback-campaign.md`, ADR-013) is reused; no new service is built. **[Open]** confirm (OI-02).
- A-2: `account-service` remains the authority for balances; cashback is a credit that reduces the amount owed.
- A-3: Campaign parameters (rate, caps, budget, enrollment) are configuration of a campaign, not code branches.

## 12. Risks and open items

### 12.1 Risks
- R-1: Caps, categories and refund handling are undefined; launching without them may breach budget or create customer-dispute exposure.
- R-2: "Additional" may be interpreted as stacking (5.5% total with an existing campaign) or as a standalone 0.5% campaign — a wrong reading changes both cost and code.
- R-3: Campaign window dates appear only in a document that disclaims being formal policy; using them without confirmation could credit out-of-scope spending.
- R-4: POC has no endpoint authorization (ADR-007); the retry and campaign administration endpoints are unauthenticated in this environment.

### 12.2 Assumptions
- The three-month scheme is delivered as campaign configuration on the existing marketing capability.

### 12.4 Consistency notes found while reading
- D-01: S3 disclaims its own parameters ("not approved formal campaign policy") while also stating "confirmed scope"; only the business owner can promote them.
- D-02: S3 says "no enrollment step"; `enrollmentRequired` is a per-campaign flag, so this is expressible as an explicit `false` rather than a conflict — but it must be set deliberately, since the sample campaign uses `true` (OI-05).
- D-03: The Teams asset list cites ADR-009 (old marketing module, `reward_credit`), while the baseline README and ADR-013 state ADR-009 was removed and `account_credit` replaced `reward_credit`. The PRD currently follows ADR-013.
- D-04: S3 requires rejecting amounts that are not a whole number of cents; the current evaluation path only rejects amount ≤ 0 and rounds `12.345` to `12.35`. REQ-009 is therefore not satisfied by the baseline (needs a decision: fix the code or relax the rule).
- D-05: Evaluation iterates over every ACTIVE campaign, so "additional 0.5%" is naturally expressible as a second campaign on top of an existing one; the same mechanism also means any other active campaign stacks silently, so exclusivity between campaigns must be decided (OI-03).
- D-06: The window is matched on the transaction date (`occurredAt.toLocalDate()`), using the server's local date; the timezone/basis question in OI-07 is therefore real, not cosmetic.

## 13. Compliance notes
- Cashback changes the amount owed, so every award must be traceable to transaction ID, campaign ID and credit ID (audit trail).
- Campaign budget usage must be visible to finance to prevent over-issue.
- No PAN or sensitive data in logs; masking rules follow the project's existing conventions.
- Production authorization is out of scope of this POC but must be closed before any real launch (R-4).
- This document is a demo preparation artifact; it does not constitute a regulatory or compliance conclusion.
