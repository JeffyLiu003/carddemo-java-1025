## 1. 背景与目标

### 1.1 业务背景

现有营销能力已支持高端卡期限返现活动：系统内存在活动 `PLATINUM_3M_CASHBACK`（白金卡，2026-10-01 起 3 个月，结束 2026-12-31，费率 5%，消费门槛 50.00 元，单笔上限 30.00 元，客户累计上限 300.00 元，活动预算 50000.00 元，需报名，状态 ACTIVE；来源：`services/marketing-service/src/main/resources/db/migration/V2__marketing_seed.sql`，属既有系统事实）。

本次诉求是在该能力之上，对白金卡客户未来 3 个月的消费**额外增加 0.5% 返现**。诉求本身只有一句话，未登记活动起止日期、叠加方式、门槛、上限、预算、报名策略与退款处理，需要在本节点澄清后再进入开发。

### 1.2 业务目标

| 目标 | 量化指标 | 确认状态 |
|------|----------|----------|
| 提升白金卡客户用卡意愿 | 原始需求未登记目标指标（活动期消费额、参与客户数、预算使用率的目标值均缺失） | 待确认（Q10） |
| 准确发放额外返现 | 合格交易返现 = min(消费金额 × 0.5%, 单笔上限, 客户剩余额度, 活动剩余预算)，HALF_UP 保留 2 位；同一活动同一交易仅发放一次 | 计算口径已由开发者定值（Q2、Q6，未登记），幂等沿用既有系统事实 |
| 不重复计发 | 同一交易在同一活动内不重复发放；与既有 PLATINUM_3M_CASHBACK 的重叠处理明确 | 已由开发者定值为独立活动叠加（Q2，未登记） |
| 营销异常不阻塞账务 | 返现评估或贷记失败只记录 WARN，交易入账不回滚，返现保留 PENDING 可重试 | 已由 ADR-013 决定（既有系统事实） |

### 1.3 术语表

| 术语 | 定义 |
|------|------|
| 额外返现 | 相对客户既有返现权益之上追加的返现比例，本次为 0.5% |
| 活动 | marketing-service 中 `campaign` 记录，含起止日期、产品圈选、费率、门槛、上限与预算 |
| 返现记录 | `reward_grant` 记录，状态为 PENDING / GRANTED / FAILED，按 `(campaign_id, transaction_id)` 唯一 |
| 贷记 | marketing-service 调用 account-service `POST /api/v1/accounts/{accountId}/credits` 冲减账户欠款，`creditId` 幂等 |
| 报名 | 客户在活动内登记（`enrollment`），`enrollment_required=true` 时未报名不予返现 |

## 3. 范围定义

### 3.1 In-Scope / Out-of-Scope

**In-Scope**

- 以活动配置方式承载「白金卡 + 3 个月 + 额外 0.5%」的返现规则（新增活动或调整既有活动，方式待确认 Q2）。
- 资格判定：产品等级 PLATINUM、交易日期在活动期、报名策略、消费门槛。
- 返现计算、单笔上限、客户累计上限、活动预算控制。
- 返现入账、幂等、失败保留 PENDING 与人工重试。
- 客户可见性（活动列表、我的返现、待入账）与运营效果查看。
- 返现记录与审计留痕。

**Out-of-Scope**

- 积分、A/B 实验、复杂客群规则 DSL、跨实例分布式锁（ADR-013 已声明不在本期）。
- 账单分期、取现、手续费等其他计费规则的改造。
- 生产级鉴权与网关（ADR-007 声明 POC 不做，生产化前另行实施）。
- 营销活动触达（短信、App 推送）与客户分群画像。

### 3.2 假设与依赖

| 编号 | 假设 / 依赖 | 说明 |
|------|-------------|------|
| A-01 | marketing-service 可配置任意费率活动 | 费率字段 `cashback_rate` 支持 0～1，0.5% 即 0.005 |
| A-02 | account-service 提供贷记接口且 `creditId` 幂等 | `POST /api/v1/accounts/{accountId}/credits`，余额可负 |
| A-03 | transaction-service 在入账成功后调用评估接口 | `POST /api/v1/reward-evaluations`，失败只 WARN |
| A-04 | 账户 `product_code` 能准确标识白金卡 | 现有按额度分档回填，需业务确认是否等同卡产品等级（Q7） |
| A-05 | 消费金额为交易入账金额且已含币种折算 | 多币种与汇率口径未定义（Q3） |

### 4.2 详细功能需求

#### REQ-2026-005-01 活动参数配置（REQ-CB-01）

**功能描述**：由营销运营在 `#/premium-campaigns` 创建或调整活动，承载「白金卡 + 3 个月 + 额外 0.5%」。活动初始为 DRAFT，发布后为 ACTIVE，暂停为 PAUSED，结束为 ENDED。

**字段级需求表**：

| 字段 | 类型 | 必填 | 格式/校验 | 默认值 | 来源 |
|------|------|------|----------|--------|------|
| code | string(64) | 是 | 唯一，大写字母与下划线 | 无 | 运营填写（待确认命名，Q1） |
| name | string(120) | 是 | 非空，≤120 字符 | 无 | 运营填写 |
| startDate | date | 是 | 活动首日；具体日期待确认（Q1） | 无 | 运营填写 |
| durationMonths | int | 是 | 1～24；本需求为 3 | 无 | 运营填写（原始需求：3 个月） |
| endDate | date | 是 | = startDate + durationMonths − 1 天（PC-01） | 计算值 | 系统计算 |
| eligibleProductCodes | string | 是 | 逗号分隔，本需求为 PLATINUM | 无 | 运营填写 |
| minTransactionAmount | decimal(12,2) | 是 | > 0；现活动为 50.00，是否沿用待确认（Q3） | 无 | 运营填写 |
| cashbackRate | decimal(6,6) | 是 | 0～1；本需求为 0.005（0.5%） | 无 | 运营填写（原始需求） |
| maxCashbackPerTransaction | decimal(12,2) | 是 | > 0；数值待确认（Q4） | 无 | 运营填写 |
| maxCashbackPerCustomer | decimal(12,2) | 是 | > 0；数值待确认（Q4） | 无 | 运营填写 |
| budget | decimal(12,2) | 是 | > 0；数值待确认（Q4） | 无 | 运营填写 |
| enrollmentRequired | boolean | 是 | 本活动是否需报名待确认（Q5） | 无 | 运营填写 |
| status | string(16) | 是 | DRAFT / ACTIVE / PAUSED / ENDED | DRAFT | 状态机 |

| 异常场景 | 系统行为 | 错误码 | 运营提示 |
|---------|---------|--------|---------|
| 费率为 0 或大于 1 | 拒绝创建 | `INVALID_CAMPAIGN` | 「返现率需大于 0 且不超过 1」 |

| code 重复 | 拒绝创建 | `CAMPAIGN_CODE_DUPLICATE` | 「活动编码已存在」 |
| 开始日期早于当日且试图发布 | 按既有窗口规则处理，是否允许待确认（Q1） | 待定义 | 待定义 |

#### REQ-2026-005-02 与既有活动的叠加控制（REQ-CB-02）

**功能描述**：明确「额外 0.5%」与既有 `PLATINUM_3M_CASHBACK` 的关系。评估接口对每个 ACTIVE 活动独立判定，`reward_grant` 唯一键为 `(campaign_id, transaction_id)`；若两个活动同时 ACTIVE 且窗口重叠，同一笔交易会各发一笔返现。

**字段级需求表**：

| 字段 | 类型 | 必填 | 格式/校验 | 默认值 | 来源 |
|------|------|------|----------|--------|------|
| 叠加方式 | 枚举 | 是 | `NEW_CAMPAIGN`（新增独立活动，与既有活动并存）或 `RATE_UPLIFT`（将既有活动费率由 0.05 调至 0.055） | 无 | 待确认（Q2） |
| 窗口重叠检查 | boolean | 是 | 若选择 `NEW_CAMPAIGN` 且与既有白金活动窗口重叠，须配置互斥手段（结束既有活动，或按业务确认允许双发） | 无 | 待确认（Q2） |

**异常矩阵**：

| 异常场景 | 系统行为 | 错误码 | 提示 |
|---------|---------|--------|------|
| 两个白金活动同时 ACTIVE 且窗口重叠 | 同一交易双发返现（当前引擎行为），须在发布前人工确认 | 无（现状行为） | 运营侧确认提示 |
| 选择 `RATE_UPLIFT` 但既有活动已产生历史返现 | 历史记录保持原费率，新交易按新费率 | 无 | 无 |

#### REQ-2026-005-03 资格判定（REQ-CB-03）

**功能描述**：逐笔交易按「产品资格 → 活动窗口 → 报名 → 消费门槛」判定；判定顺序与 `RewardService.skipReason` 一致。

**字段级需求表**：

| 字段 | 类型 | 必填 | 格式/校验 | 默认值 | 来源 |
|------|------|------|----------|--------|------|
| accountId | string(20) | 是 | 存在账户，非空 | 无 | 评估请求 |
| cardNumber | string(19) | 否 | 卡号后四位用于展示 | 空 | 评估请求 |
| customerId | string(20) | 是 | 非空 | 无 | 评估请求 |
| amount | decimal(12,2) | 是 | > 0；低于门槛不返现 | 无 | 评估请求 |
| occurredAt | datetime | 是 | 不得为空，取日期判定窗口 | 无 | 评估请求 |
| productCode | string(16) | 是 | 取自 account-service，须等于 PLATINUM | 无 | account-service |

**异常矩阵**：

| 异常场景 | 系统行为 | 错误码 / 跳过原因 | 用户提示 |
|---------|---------|------------------|---------|
| 账户非白金卡 | 跳过该活动 | `PRODUCT_NOT_ELIGIBLE` | 前台不展示该活动 |
| 交易日期不在活动期 | 跳过 | `OUTSIDE_WINDOW` | 无提示（不发放） |
| 需报名但未报名 | 跳过 | `NOT_ENROLLED` | 「请先报名参与活动」 |
| 消费金额低于门槛 | 跳过 | `AMOUNT_TOO_LOW` | 无提示（不发放） |
| 账户不存在或 account-service 不可用 | 评估失败，交易不受影响 | `REMOTE_SERVICE_UNAVAILABLE` | 无（仅日志 WARN） |
| 请求缺少交易号、账户号或客户号 | 拒绝评估 | `INVALID_TRANSACTION_ID` / `INVALID_ACCOUNT_ID` / `INVALID_CUSTOMER_ID` | 调用方修正 |

#### REQ-2026-005-04 返现计算与上限（REQ-CB-04）

**功能描述**：返现 = min(消费金额 × 0.005, 单笔上限, 客户剩余额度, 活动剩余预算)，HALF_UP 保留 2 位；结果为 0 时不发放。客户累计上限按 PENDING 与 GRANTED 记录合计；预算在创建 PENDING 时预占。

**字段级需求表**：

| 字段 | 类型 | 必填 | 校验 | 说明 |
|------|------|------|------|------|
| transactionAmount | decimal(12,2) | 是 | > 0 | 消费金额 |
| cashbackRate | decimal(6,6) | 是 | = 0.005 | 本活动费率（Q2 决定承载方式） |
| proportional | decimal(12,2) | 是 | HALF_UP 2 位 | 金额 × 费率 |
| maxCashbackPerTransaction | decimal(12,2) | 是 | > 0 | 单笔上限（Q4） |
| customerRemaining | decimal(12,2) | 是 | ≥ 0 | 客户上限 − 已发放（PENDING + GRANTED） |
| budgetRemaining | decimal(12,2) | 是 | ≥ 0 | 预算 − 已消耗 |
| cashbackAmount | decimal(12,2) | 是 | ≥ 0，2 位 | 最终发放金额 |

**计算示例（示例口径，费率 0.5% 已确认，其余数值仅为演示）**：

| 消费金额 | 金额 × 0.5% | HALF_UP 2 位 | 说明 |
|---------|-------------|--------------|------|
| 120.00 | 0.6000 | 0.60 | 与设计库示例一致 |
| 1000.00 | 5.0000 | 5.00 | 未触及任何上限时全发 |
| 30.10 | 0.1505 | 0.15 | 第三位小数为 5 以下 |
| 1.00 | 0.0050 | 0.01 | 半分向上（HALF_UP） |
| 0.30 | 0.0015 | 0.00 | 结果为 0 不发放 |

**异常矩阵**：

| 异常场景 | 系统行为 | 跳过原因 | 说明 |
|---------|---------|----------|------|
| 计算结果为 0 | 创建跳过记录，不发返现 | `AMOUNT_TOO_LOW` | 与实现一致 |
| 客户累计已达上限 | 跳过 | `CUSTOMER_CAP_REACHED` | 上限按活动与客户维度 |
| 活动预算耗尽 | 跳过 | `BUDGET_EXHAUSTED` | 预算按活动维度 |
| 并发交易同时占用客户上限或预算 | 单实例内以活动行锁串行化；多实例存在超额风险 | 无 | 见 R-02 |
| 金额为空或 ≤ 0 | 拒绝评估 | `INVALID_AMOUNT` | 调用方修正 |

#### REQ-2026-005-05 返现入账、幂等与重试（REQ-CB-05）

**功能描述**：返现记录先落 PENDING 并预占预算，随后同步调用 account-service 贷记；成功置 GRANTED 并记录发放时间，失败保留 PENDING 与失败原因，供 `POST /api/v1/rewards/{rewardId}/retry` 人工重试。

**字段级需求表**：

| 字段 | 类型 | 必填 | 校验 | 来源 |
|------|------|------|------|------|
| rewardId | uuid | 是 | 唯一，同时作为贷记 `creditId` | marketing-service 生成 |
| campaignId | uuid | 是 | 关联活动 | campaign |
| transactionId | string(64) | 是 | 与 campaignId 联合唯一（PC-08） | 评估请求 |
| cashbackAmount | decimal(12,2) | 是 | > 0 | 计算 |
| status | string(16) | 是 | PENDING / GRANTED / FAILED | 状态机 |
| grantedAt | datetime | 否 | GRANTED 时必填 | 贷记成功时刻 |
| failureReason | string(256) | 否 | PENDING 且贷记失败时记录 | 下游异常信息 |

**异常矩阵**：

| 异常场景 | 系统行为 | 错误码 | 用户提示 |
|---------|---------|--------|---------|
| account-service 超时或 5xx | 记录保留 PENDING 与原因，交易不回滚 | 无（内部） | 前台展示「待入账」 |
| 同一交易重复评估 | 返回既有跳过原因 `ALREADY_EVALUATED`，不重复发放 | `ALREADY_EVALUATED` | 无 |
| 同一 rewardId 重复贷记 | account-service 按 creditId 幂等，返回当前账户 | 无 | 无 |
| 对已 GRANTED 记录重试 | 直接返回当前记录，不再贷记 | 无 | 无 |
| 重试仍失败 | 保持 PENDING，可继续重试 | 无 | 「待入账，稍后重试」 |
| 重试时活动或记录不存在 | 返回 404 | `REWARD_NOT_FOUND` / `CAMPAIGN_NOT_FOUND` | 调用方核查 |

#### REQ-2026-005-06 客户可见性与运营效果（REQ-CB-06）

**功能描述**：客户在 `#/premium-offers` 查看可用活动、资格、我的返现与待入账记录；运营在 `#/premium-campaigns` 查看活动列表、报名列表与效果（报名数、奖励笔数、发放成功数、返现总额、预算使用率、转化率）。

| 项 | 要求 | 校验 |
|----|------|------|
| 客户活动列表 | 仅返回与查询账户匹配且满足资格的活动 | 传非白金账户时列表不含本活动 |
| 我的返现 | 按客户或账户分页返回，含活动编码、金额、状态、时间 | 分页 `{items,page,size,total}` |
| 待入账重试 | 客户可对自身 PENDING 记录发起重试 | 非本人记录返回 404 |
| 效果指标 | 预算使用率 = 已消耗预算 ÷ 预算；转化率 = 有返现客户数 ÷ 报名数 | 数值与返现记录一致 |

#### REQ-2026-005-07 返现记录与审计留痕（REQ-CB-07）

**功能描述**：返现记录保存活动编码、交易号、卡号后四位、客户号、消费金额、返现金额、状态与时间；评估失败只记 WARN 日志（含 transactionId，不含卡号全量）；活动发布、暂停、结束与人工重试均留痕。

| 编号 | 规则 | 来源 | 优先级 | 验证点 |
|------|------|------|--------|--------|
| BR-CB-01 | 返现比例在既有返现之上额外增加 0.5% | 原始需求（requirement-v1，2026-11-02） | 必须 | 配置费率 0.005；1000.00 元交易返 5.00 元 |

## 9. 场景矩阵

| 类型 | 场景 | 角色 / 数据 | 接口 | 预期 |
|------|------|-------------|------|------|
| 主流程 | 白金账户报名后消费 1000.00（活动期、无上限触及） | 客户 000000001 / 账户 00000000006 | 评估 → 贷记 | 返现 5.00，状态 GRANTED，欠款减少 5.00 |
| 主流程 | 运营创建并发布活动 | 运营 | POST `/campaigns` → `/activate` | 活动 ACTIVE，客户活动列表可见 |

| 边界 | 消费 1.00 | 白金账户 | 评估 | 返现 0.01（HALF_UP 半分向上） |
| 边界 | 消费 0.30（低于门槛时同样跳过） | 白金账户 | 评估 | 计算结果 0.00，跳过 `AMOUNT_TOO_LOW` |

## 10. 验收标准（可执行化）

## 11. 依赖与约束

### 11.1 依赖

| 依赖 | 用途 | 失败影响与处理 |
|------|------|---------------|
| marketing-service | 活动、报名、返现计算与记录 | 不可用时交易照常入账，返现延迟，恢复后重试 |

### 11.2 影响分析

| 维度 | 影响 |
|------|------|
| 代码 | 首选零代码改动（活动配置）；若采用 `RATE_UPLIFT` 则为数据变更 + 活动审计；若需互斥或退款扣回，则涉及 marketing-service 评估逻辑与奖励冲正 |
| 数据 | `campaign`（新增或更新 1 条）、`reward_grant`（新增返现记录）、`account_credit`（新增贷记记录） |
| 接口 | 复用现有 9 个接口；若需退款扣回则新增冲正接口（待 Q8 决定） |
| 配置 | 活动参数、`MARKETING_SERVICE_URL`、`MARKETING_ENABLED` |
| 前台 | `#/premium-offers` 活动卡片与返现列表；`#/premium-campaigns` 创建表单提示 |
| 测试 | 费率与舍入边界、窗口边界、门槛、上限、预算、幂等、贷记失败重试、活动重叠 |
| 文档 | 本 PRD、活动运营说明、API 目录（若新增冲正接口） |

### 11.3 约束

- 金额与费率统一 `BigDecimal` / `numeric`，禁止浮点。
- 返现只能由系统按评估结果发放，运营不得手工改余额。
- 预算与上限为单实例保护；多实例部署前须补行锁或条件更新。
- 不引入 MQ，沿用同步调用（ADR-013）；营销不可用不得影响账务。
- POC 鉴权沿用 ADR-007，任何非环回地址暴露前须完成网关方案。

## 12. 风险与假设

### 12.1 风险与应对

| 编号 | 风险 | 影响 | 应对 |
|------|------|------|------|
| R-01 | 既有 `PLATINUM_3M_CASHBACK`（2026-10-01～2026-12-31，费率 5%）与本活动窗口重叠且均 ACTIVE 时，同一交易双发返现 | 预算超支、客户获得双重权益、对账差异 | 发布前显式确认叠加方式（Q2）；重叠期只保留一个 ACTIVE 活动或经业务批准双发 |
| R-02 | 预算与客户上限为单实例保护 | 多实例并发下可能超额发放 | 单实例演示；扩容前补行锁或数据库条件更新 |
| R-03 | 「额外 0.5%」口径歧义（新增独立活动叠加，或将既有费率 5% 调为 5.5%） | 返现金额与预算口径差异，返工风险 | 需求澄清阶段确认（Q2），确认前不开发 |
| R-04 | 起止日期未登记，设计库文档参数自述「不是正式政策」 | 活动窗口错误导致多返或少返 | 由业务负责人确认起止日期（Q1） |
| R-05 | 退货、退款、拒付未定义返现处理 | 客户获不当得利、账务不平 | 确认扣回或保留策略（Q8）；若需扣回则新增冲正能力 |
| R-06 | POC 接口级鉴权缺失（ADR-007） | 未授权调用可创建活动或查询返现 | 仅环回/本地环境运行；生产化前实施网关 |
| R-07 | 账户 `product_code` 由额度分档回填，未必等同卡产品等级 | 非白金客户误判或白金客户漏判 | 确认判定口径（Q7）；必要时改为按卡产品取数 |

### 12.2 假设

- 本期以活动配置为主要交付手段，不改动交易入账与账户余额语义。
- 活动期内所有白金卡合格消费均参与评估，不做客户白名单细分。
- 返现以人民币计，交易金额已由上游完成币种统一（待 Q3 确认）。
- 客户累计上限按活动与客户维度计算，不跨活动合并。

### 12.3 待确认事项（责任方与影响）

| 编号 | 待确认事项 | 为什么必须确认 | 责任方 | 状态 |
|------|-----------|----------------|--------|------|
| Q1 | 活动起止日期与「未来 3 个月」起算口径（自发布日次日起算，或固定自然月区间） | 决定活动窗口与验收边界；设计库文档的 2026-11-01～2027-02-01 自述非正式政策 | 业务发起方（白金卡营销负责人），由交付人陈晨汇总提交 | 开发者已定值：固定 2026-11-01～2027-01-31（未登记） |
| Q2 | 「额外 0.5%」承载方式：新增独立活动叠加，或将既有 PLATINUM_3M_CASHBACK 费率由 5% 调整为 5.5% | 决定是否双发、预算口径与代码改动范围（R-01、R-03） | 业务发起方 + 营销运营 | 开发者已定值：独立活动叠加（未登记） |
| Q3 | 返现基数与剔除项：是否剔除退款、取现、手续费、分期本金；是否含线上与境外消费；多币种折算口径 | 直接决定返现金额与对账结果 | 业务发起方 + 账务 | 待确认 |
| Q4 | 单笔上限、客户累计上限、活动总预算的取值 | 缺少数值无法配置活动，也无法设定验收预期 | 业务发起方 + 财务预算 | 开发者已定值：30.00 / 300.00 / 50000.00（未登记） |
| Q5 | 是否要求报名（`enrollmentRequired`），以及报名入口是否对外可见 | 决定客户是否需先报名才可获返现 | 业务发起方 | 开发者已定值：需报名（未登记） |
| Q6 | 消费门槛是否沿用 50.00 元；是否设置最低返现金额 | 影响小额交易是否参与，及 0.00 结果的处理 | 业务发起方 | 开发者已定值：门槛 50.00（未登记） |
| Q7 | 白金卡判定口径：按账户 `product_code` 还是按卡产品等级；附属卡是否单独计入客户上限 | 判定错误会造成多发或漏发 | 业务发起方 + 卡产品 | 待确认 |
| Q8 | 退款、撤销、拒付场景的返现处理（扣回、保留或人工处理） | 未定义将导致不当得利与账务差异（R-05） | 业务发起方 + 账务 + 合规 | 开发者已定值：本期不做冲正（未登记） |
| Q9 | 活动参数由谁维护、发布审批人是谁、暂停/结束的触发条件 | 运营权责不清会导致误发布 | 营销运营负责人 | 待确认 |
| Q10 | 业务目标指标（活动期消费额、参与客户数、预算使用率目标）、优先级与目标版本 | 缺少目标无法评估活动效果与排期 | 业务发起方 + 产品负责人 | 待确认 |

> 上表中 Q1/Q2/Q4/Q5/Q6/Q8 已由开发者在 2026-11-02 给出实现取值（见第 0 章 E 层与 `docs/design/18-platinum-extra-cashback.md` §3），但均未在 `agreement.confirmations` 登记，本文档不将其表述为业务已确认的政策；Q3/Q7/Q9/Q10 仍无任何依据，保持待确认。

## 13. 合规标注

| 维度 | 标注 |
|------|------|
| 监管（模拟） | 参照《商业银行信用卡业务监督管理办法》关于营销活动信息披露与客户知情的要求：活动规则、期限、上限应向客户明示。本文件为演示材料，不构成监管合规结论。 |
| 制度（模拟） | 参照行内营销活动管理办法（模拟编号 MKT-POLICY-2026）：活动须经业务与财务预算审批后发布，活动参数变更留痕。 |
| 资金安全 | 返现属客户资金权益，只能由系统按评估结果贷记；禁止人工直接修改余额；贷记幂等且可对账。 |
| SoD（职责分离） | 活动创建人与发布审批人应为不同角色；运营不可直接操作账户余额。 |
| 隐私（模拟） | 参照《个人信息保护法》：评估仅使用交易号、账户号、客户号、卡号与金额；日志不记录卡号全量。 |
| 审计 | 活动状态变更、返现发放、人工重试全量留痕，审计留存 3 年。 |
| 结论 | 本需求为演示需求，费率 0.5% 已由原始需求登记，其余活动参数与口径待业务确认；投产前需业务、财务、合规会签。 |
