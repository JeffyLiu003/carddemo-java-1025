## 1. 背景与目标

### 1.1 业务背景

基线 `main` 已包含高端卡消费返现能力（`docs/design/17-premium-cashback-campaign.md`、ADR-013）：`marketing-service` 管理活动、报名与返现记录，交易入账成功后由 `transaction-service` 调用 `POST /api/v1/reward-evaluations` 评估，返现通过 `POST /api/v1/accounts/{accountId}/credits` 实时冲减欠款，贷记失败保留 `PENDING` 可重试。

本次业务诉求：**针对白金卡客户未来 3 个月的消费，额外增加 0.5% 的消费返现。**

「额外」的落地方案按 D-01 确定为在既有白金卡活动之上叠加一笔独立的 0.5% 返现活动（费率 `0.005`），既有 5% 活动配置不变。备选方案（把既有活动费率提高到 5.5%）不采用：它会改变正在运行活动的返现口径与已发返现实体，且无法独立启停或独立回退。

### 1.2 业务目标（可量化）

| 目标 | 量化指标 | 依据 |
|------|---------|------|
| 提升白金卡客户活动期用卡与消费 | 活动期白金卡客户消费额较活动前 3 个月提升 ≥ 5% | D-02 |
| 落实额外 0.5% 返现 | 活动期内达标消费按 0.5% 额外返现，计算误差 0 分 | D-01、D-04 |
| 预算可控 | 活动累计返现 ≤ 50 000.00 元；单客户累计 ≤ 300.00 元；单笔 ≤ 30.00 元 | D-04 |
| 资金安全 | 同一交易同一活动不重复返现；返现入账幂等 | 基线能力（`RewardService.evaluate`、account `creditId` 幂等），BR-CB-06/07 |

### 1.3 术语表

| 术语 | 定义 |
|------|------|
| 活动（campaign） | 按卡产品等级圈选、含起止日期、费率、单笔/客户上限与预算的返现配置，状态为 `DRAFT`/`ACTIVE`/`PAUSED`/`ENDED` |
| 额外返现 | 本次需求新增的 0.5% 返现部分，以独立活动形式与既有白金卡活动并行（D-01） |
| 活动窗口 | `[startDate, endDate]`，`endDate = startDate + durationMonths 月 - 1 天`（PC-01） |
| 返现率 | 活动配置的返现比例，取值 0–1 的 `BigDecimal`（PC-02） |
| 单笔上限 | 单笔交易可获得的最大返现额 `maxCashbackPerTransaction` |
| 客户累计上限 | 同一客户在同一活动内的累计返现上限 `maxCashbackPerCustomer` |
| 活动预算 | 活动可发放返现总额 `budget`；创建 `PENDING` 时预占 `consumedBudget`（PC-09） |
| 幂等键 | 返现评估幂等键 `(campaignId, transactionId)`；贷记幂等键 `creditId = rewardId`（PC-08、PC-10） |
| `PENDING` / `GRANTED` / `FAILED` | 返现记录状态：待入账 / 已入账 / 入账失败 |
| 消费类交易 | `typeCode = "01"`（Purchase）的入账交易；类别明细由 `GET /api/v1/transaction-categories?typeCode=01` 提供 |

## 3. 范围定义

### 3.1 In-Scope / Out-of-Scope

**In-Scope**

- 仅白金卡（产品编码 `PLATINUM`）客户的消费类交易返现；其他卡产品不参与。
- 活动窗口 2026-11-13 至 2027-02-12 内的消费返现（D-03）；窗口外交易不参与。
- 额外 0.5% 返现的计算与入账（冲减欠款）、幂等与失败重试。
- 与既有白金卡活动并行评估（同一交易可命中多个 `ACTIVE` 活动，`grants` 数组返回多条）。
- `transaction-service` 仅对消费类交易触发返现评估的过滤能力（D-07）。
- 客户可见返现记录与活动资格查询；运营活动配置与效果查看。

**Out-of-Scope**

- 金卡/普通卡持卡人；取现、费用、利息、分期类交易（D-07 明确不参与）。
- 积分、权益兑换、A/B 实验、复杂客群 DSL（ADR-013 决策 6）。
- 历史交易追溯补发、跨期批量补偿（D-08）。
- 报名流程：本需求无报名步骤，`enrollmentRequired=false`（D-05）。
- 退款/撤销/拒付的返现回收实现（本期不回收，D-06）。
- 新鉴权/网关能力（ADR-007 已知缺口，本期不补，D-10）。

### 3.2 假设与依赖

| 编号 | 假设/依赖 | 说明 |
|------|----------|------|
| A-01 | `marketing-service` 已具备活动/报名/返现能力 | 基线 `main` 已交付，见 `docs/design/17` §3 |
| A-02 | `transaction-service` 入账后调用返现评估 | 受 `MARKETING_ENABLED` 开关控制，失败只记 WARN |
| A-03 | `account-service` 贷记接口可用且 `creditId` 幂等 | `POST /api/v1/accounts/{accountId}/credits` |
| A-04 | 账户产品编码可从 `account-service` 读取 | `AccountClient.creditPosition` 返回 `productCode` |
| A-05 | 活动以配置形式下发，费率/期限/上限/预算无需改表 | 费率、期限、上限、预算均为 `campaign` 字段 |
| A-06 | 金额统一 `BigDecimal` / `numeric(12,2)`，HALF_UP 2 位 | `RewardCalculator` |
| A-07 | 消费类交易可按 `typeCode = "01"` 判定 | 交易类型字典 `GET /api/v1/transaction-types`；`PostingService` 已持有 `typeCode` |

### 4.2 详细功能需求

#### REQ-CB-01 额外返现活动配置与发布

**功能描述**：运营创建一份白金卡额外返现活动，费率为 0.5%（`0.005`），窗口 2026-11-13 至 2027-02-12，圈选产品 `PLATINUM`，无报名要求；发布后状态由 `DRAFT` 变为 `ACTIVE` 才参与评估。

**字段级需求表**：

| 字段 | 类型 | 必填 | 格式/校验 | 默认值 | 来源 |
|------|------|------|----------|--------|------|
| code | string(64) | 是 | 全局唯一，固定 `PLATINUM_EXTRA_0_5_3M` | 无 | D-01 |
| name / description | string(128/256) | 是/否 | 描述须说明「在既有白金卡活动之上额外返现 0.5%」 | 无 | 运营填写 |
| startDate | date | 是 | 2026-11-13（含） | 无 | D-03 |
| durationMonths | int | 是 | 1–24，本需求固定 3 | 3 | D-03 |
| endDate | date | 是 | 系统计算 `startDate + 3 月 - 1 天` = 2027-02-12 | 计算值 | PC-01、D-03 |
| eligibleProductCodes | string | 是 | 仅 `PLATINUM` | 无 | 原始需求 |
| cashbackRate | decimal | 是 | `0.005`，取值 0–1 | 无 | D-01（0.5%） |
| minTransactionAmount | decimal(12,2) | 是 | `50.00`，≥ 0.01 | 50.00 | D-04 |
| maxCashbackPerTransaction | decimal(12,2) | 是 | `30.00`，> 0 | 30.00 | D-04 |
| maxCashbackPerCustomer | decimal(12,2) | 是 | `300.00`，> 0 | 300.00 | D-04 |
| budget | decimal(12,2) | 是 | `50000.00`，> 0 | 50000.00 | D-04 |
| enrollmentRequired | boolean | 是 | `false` | false | D-05 |

**异常矩阵**：

| 异常场景 | 系统行为 | 错误码 | 提示 |
|---------|---------|--------|------|
| `code` 已存在 | 创建被拒 | `CAMPAIGN_CODE_EXISTS`（409） | 「活动编码已存在」 |
| `durationMonths` 不在 1–24 | 创建被拒 | `INVALID_CAMPAIGN_WINDOW`（400） | 「活动期限须为 1–24 个月」 |
| 费率不在 0–1、上限或预算 ≤ 0 | 创建被拒 | `INVALID_CAMPAIGN_PARAMETERS`（400） | 「费率/上限/预算取值不合法」 |
| 产品等级为空或不含 `PLATINUM` | 创建被拒 | `INVALID_CAMPAIGN_PARAMETERS`（400） | 「须指定适用产品等级」 |
| 发布时活动处于 `ACTIVE` | 幂等返回当前状态 | 无（幂等） | 「活动已发布」 |
| 结束/暂停 `ENDED` 活动 | 拒绝状态迁移 | `CAMPAIGN_NOT_PENDING`（409） | 「活动已结束」 |

#### REQ-CB-02 消费类交易的返现评估与多活动叠加

**功能描述**：消费类交易入账成功后触发返现评估，遍历全部 `ACTIVE` 活动；命中既有白金卡活动与本次额外返现活动时，各自独立生成返现记录，`grants` 返回多条。非消费类交易不触发评估（D-07）：`transaction-service` 在调用评估前按 `typeCode` 过滤。

**字段级需求表**：

| 字段 | 类型 | 必填 | 格式/校验 | 默认值 | 来源 |
|------|------|------|----------|--------|------|
| transactionId | string(32) | 是 | 非空，交易号 | 无 | transaction-service |
| accountId | string(20) | 是 | 非空，账户存在 | 无 | transaction-service |
| customerId | string(20) | 是 | 非空 | 无 | transaction-service |
| cardNumber | string(19) | 否 | 掩码前不落日志 | 无 | transaction-service |
| amount | decimal(12,2) | 是 | > 0；≤ 0 或非两位小数拒绝 | 无 | transaction-service |
| occurredAt | datetime | 是 | 不得为空；按 `toLocalDate()` 判定窗口 | 无 | transaction-service |
| typeCode | string(2) | 是 | 仅 `01`（Purchase）触发评估 | 无 | 交易记录（D-07） |

**异常矩阵**：

| 异常场景 | 系统行为 | 返回标记/错误码 | 说明 |
|---------|---------|----------------|------|
| 非消费类交易（`typeCode` ≠ `01`） | 不调用返现评估 | 无调用 | D-07；入账按原流程完成 |
| 交易日期在活动窗口外 | 跳过该活动 | `skipped.reason=OUTSIDE_WINDOW` | 不影响其他活动 |
| 账户产品编码非 `PLATINUM` | 跳过 | `PRODUCT_NOT_ELIGIBLE` | 普通卡不参与 |
| 交易金额 < 门槛 50.00 | 跳过 | `AMOUNT_TOO_LOW` | D-04 |
| 同一活动同一交易重复评估 | 跳过，不重复发奖 | `ALREADY_EVALUATED` | 幂等键 `(campaignId, transactionId)` |
| 客户累计返现已达上限 300.00 | 跳过 | `CUSTOMER_CAP_REACHED` | D-04 |
| 活动预算耗尽 | 跳过 | `BUDGET_EXHAUSTED` | 预算创建 `PENDING` 时预占 |
| 请求金额 ≤ 0 或格式非法 | 整体请求拒绝 | `INVALID_AMOUNT`（400） | 无效金额拒绝处理（消费返现规则第 9 行） |
| `transactionId`/`accountId` 缺失 | 整体请求拒绝 | `INVALID_TRANSACTION_ID` / `INVALID_ACCOUNT_ID`（400） | — |
| `account-service` 不可用（读取产品等级） | 评估失败，入账不回滚 | 调用方记 WARN | 营销失败不影响资金事实 |

#### REQ-CB-03 返现入账、幂等与失败重试

**功能描述**：返现记录创建为 `PENDING` 后同步调用账户贷记，成功置 `GRANTED` 并记录入账时间；失败保留 `PENDING` 与失败原因，可人工重试，重试仍幂等。

**字段级需求表**：

| 字段 | 类型 | 必填 | 格式/校验 | 默认值 | 来源 |
|------|------|------|----------|--------|------|
| creditId | string(36) | 是 | = `rewardId`，账户侧唯一 | 无 | marketing-service |
| accountId | string(20) | 是 | 账户存在 | 无 | 返现记录 |
| amount | decimal(12,2) | 是 | > 0，2 位小数 | 无 | `RewardCalculator` |
| sourceType | string(16) | 是 | `CASHBACK` | `CASHBACK` | 设计 §3.2 |
| status | string(16) | 是 | `PENDING` → `GRANTED` / `FAILED` | `PENDING` | 状态机 |
| failureReason | string(128) | 否 | 失败时记录下游原因 | 空 | 贷记结果 |

**异常矩阵**：

| 异常场景 | 系统行为 | 错误码 | 处理 |
|---------|---------|--------|------|
| 账户贷记超时/不可用 | 保留 `PENDING`，记录原因 | 无（返回 PENDING 记录） | 人工重试 `POST /api/v1/rewards/{rewardId}/retry` |
| 同一 `rewardId` 重复贷记 | 返回当前账户，不重复冲减 | 幂等命中 | `account_credit.credit_id` 唯一 |
| 已 `GRANTED` 的记录再次重试 | 直接返回当前记录，不再贷记 | 幂等 | `isRetryable()` 判定 |
| `PENDING` 超过 24 小时未成功 | 触发告警并纳入人工重试清单 | 无 | D-09 |
| 返现记录不存在 | 返回 404 | `REWARD_NOT_FOUND` | — |
| 活动不存在 | 返回 404 | `CAMPAIGN_NOT_FOUND` | — |

#### REQ-CB-04 上限与预算控制

**功能描述**：返现额 = `min(消费金额 × 0.005, 单笔上限 30.00, 客户剩余额度, 活动剩余预算)`，HALF_UP 保留 2 位；客户剩余额度按 `PENDING + GRANTED` 汇总计算；预算在创建 `PENDING` 时预占。

**字段级需求表**：

| 字段 | 类型 | 必填 | 格式/校验 | 默认值 | 来源 |
|------|------|------|----------|--------|------|
| transactionAmount | decimal(12,2) | 是 | ≥ 50.00（门槛） | 无 | 交易 + D-04 |
| cashbackRate | decimal | 是 | 0–1 | 0.005 | 活动配置（D-01） |
| maxCashbackPerTransaction | decimal(12,2) | 是 | > 0 | 30.00 | 活动配置（D-04） |
| customerRemaining | decimal(12,2) | 是 | `300.00 - 已发（PENDING+GRANTED）` | 计算值 | `grants.customerCashback`（D-04） |
| budgetRemaining | decimal(12,2) | 是 | `budget - consumedBudget` | 计算值 | 活动（D-04） |
| cashbackAmount | decimal(12,2) | 是 | 上述四者最小值，HALF_UP 2 位，≥ 0 | 0 | `RewardCalculator` |

**异常矩阵**：

| 异常场景 | 系统行为 | 返回标记 | 说明 |
|---------|---------|---------|------|
| 计算结果为 0（费率 0 或额度耗尽） | 不创建返现记录 | `AMOUNT_TOO_LOW` | 结果 0 不发放 |
| 客户剩余额度 < 本次应发 | 按剩余额度发放（部分发放） | 置 `GRANTED` | 计算取 min，不超额 |
| 并发两笔交易同时预占预算 | 单实例内以活动行锁串行化 | — | 多实例需分布式锁（R-03） |
| 预算已耗尽 | 跳过 | `BUDGET_EXHAUSTED` | `consumedBudget` 不超 `budget` |

#### REQ-CB-05 客户返现记录与活动资格可见性

**功能描述**：客户按账户/客户号查询可见活动与资格，以及本人返现记录（含 `PENDING` 待入账）；页面展示额外返现总额与状态。

#### REQ-CB-07 退款/撤销/拒付的返现处理

**功能描述**：按 D-06，本期退款、撤销、拒付均不回收已发返现，也不重算。该行为作为已知限制登记（R-02），回收规则待业务与风控确认后另行实施。

**异常矩阵**：

|---------|---------|---------|------|

| 部分退款 | 不重算返现 | 返现记录保持 `GRANTED` | 同上 |
| 拒付/争议成立 | 不回收 | 返现记录保持 `GRANTED` | 与争议流程的联动方式待确认 |

## 5. 业务规则

| 编号 | 规则 | 来源 | 优先级 | 确认状态 | 验证点 |
|------|------|------|--------|---------|--------|
| BR-CB-01 | 仅 `PLATINUM` 产品账户的消费类交易参与额外返现 | 原始需求 + 消费返现规则第 9 行 | 必须 | 已确认（来源：需求原文与规则文档，2026-11-13；D-07 补充消费类限定） | 普通卡交易返回 `PRODUCT_NOT_ELIGIBLE`；非消费类不触发评估 |
| BR-CB-02 | 额外返现比例 0.5%（费率 `0.005`），返现 = 消费金额 × 0.5% | 原始需求 + 规则第 7 行（1/200） | 必须 | 已确认（D-01，来源同上） | 120.00 元 → 0.60 元 |
| BR-CB-03 | 金额以整数分计算，半分向上舍入至整分（账户显示 HALF_UP 2 位） | 规则第 7 行；`RewardCalculator` | 必须 | 已确认（来源：规则文档与基线代码） | 半分数值构造用例断言向上舍入 |
| BR-CB-04 | 仅活动窗口 2026-11-13 至 2027-02-12 内的交易参与；`endDate = startDate + 3 月 - 1 天` | PC-01、PC-03 | 必须 | 已确认（D-03） | 窗口首末日边界用例；窗口外返回 `OUTSIDE_WINDOW` |
| BR-CB-05 | 无报名步骤，`enrollmentRequired=false`，消费即参与 | 规则第 10 行「此范围没有报名步骤」 | 必须 | 已确认（D-05） | 未报名客户消费仍获得返现 |
| BR-CB-06 | 同一活动同一交易只返现一次 | PC-08、ADR-013 决策 5 | 必须 | 已确认（来源：基线设计与代码） | 重复评估返回 `ALREADY_EVALUATED`，返现记录数 1 |
| BR-CB-07 | 返现入账幂等：`creditId = rewardId` 唯一，重复调用不重复冲减 | PC-10、ADR-013 决策 3 | 必须 | 已确认（来源同上） | 同一 `rewardId` 贷记两次，余额仅变化一次 |
| BR-CB-08 | 返现额 = `min(金额×费率, 30.00, 客户剩余, 预算剩余)`，HALF_UP 2 位；门槛 50.00、客户上限 300.00、预算 50 000.00 | PC-07 | 必须 | 已确认（D-04） | 上限命中用例断言取最小值 |
| BR-CB-09 | 无效金额（≤ 0、非整数分）拒绝处理 | 规则第 9 行 | 必须 | 已确认（来源：规则文档与基线校验） | 金额 0、负数、三位小数均被拒 |
| BR-CB-10 | 额外返现与既有白金卡活动并行叠加，各自独立计算上限与预算 | `RewardService.evaluate` 遍历全部 `ACTIVE` 活动 | 必须 | 已确认（D-01） | 同一交易返回 2 条 `grants` |
| BR-CB-11 | 营销评估失败不影响交易入账 | ADR-013 决策 2、ADR-009 约束 1 | 必须 | 已确认（来源：基线设计与代码） | 停用 marketing-service 后入账成功 |
| BR-CB-12 | 退款/撤销/拒付本期不回收返现、不重算 | D-06 | 必须 | 本期行为已决定（D-06）；正式回收口径待业务与风控签认 | 退款后返现记录仍为 `GRANTED`，账户余额不回补 |

| 维度 | 指标 | 验证方法 |
|------|------|---------|

| 维度 | 要求 | 验证方法 |
|------|------|---------|

## 9. 场景矩阵

| 类型 | 场景 | 角色 | 数据/接口 | 预期 |
|------|------|------|-----------|------|
| 主流程 | 白金卡客户活动期内消费 120.00 元，命中额外返现活动 | 持卡人 | POST `/reward-evaluations` | 生成 0.60 元返现并 `GRANTED`，账户欠款减少 0.60 |
| 主流程 | 同一交易命中既有 5% 活动与额外 0.5% 活动 | 持卡人 | POST `/reward-evaluations` | `grants` 返回 2 条，各自上限与预算独立（D-01） |
| 主流程 | 费用类交易（`typeCode` ≠ `01`）入账 | 系统 | 入账 → 评估调用 | 不调用返现评估，无返现记录（D-07） |
| 边界 | 消费金额 = 起返门槛 50.00 元 | 持卡人 | POST `/reward-evaluations` | 返现 0.25 元；49.99 元返回 `AMOUNT_TOO_LOW` |
| 边界 | 消费 100.00 元产生 0.50 元返现（半分） | 持卡人 | POST `/reward-evaluations` | 0.50 元；构造 0.005 元边界值断言向上舍入至 0.01 |
| 边界 | 累计返现达到客户上限 300.00 前一笔 | 持卡人 | 连续评估 | 最后一笔按剩余额度部分发放，之后返回 `CUSTOMER_CAP_REACHED` |
| 边界 | 窗口首日 2026-11-13 与末日 2027-02-12 | 持卡人 | POST `/reward-evaluations` | 首末日均参与；2026-11-12 与 2027-02-13 返回 `OUTSIDE_WINDOW` |
| 异常 | 普通卡账户消费 | 持卡人 | POST `/reward-evaluations` | 返回 `PRODUCT_NOT_ELIGIBLE`，无返现 |
| 异常 | 同一交易号重复入账评估 | 系统 | 相同 `transactionId` 连续评估 3 次 | 返现记录仅 1 条，第 2、3 次返回 `ALREADY_EVALUATED` |
| 异常 | 活动预算耗尽后继续消费 | 持卡人 | 连续评估至预算耗尽 | 返回 `BUDGET_EXHAUSTED`，`consumedBudget` 不超 50 000.00 |
| 异常 | 账户贷记失败 | 系统 | 停用 account-service 后评估 | 返现记录 `PENDING` 且记录失败原因；恢复后重试成功置 `GRANTED`，仅贷记一次 |
| 异常 | 交易金额为 0 或负数 | 系统 | POST `/reward-evaluations` | 400 `INVALID_AMOUNT` |
| 异常 | 全额退款后返现已发放 | 系统 | 退款交易入账 | 返现不回收，记录保持 `GRANTED`（D-06） |
| 权限 | 客户尝试创建/发布活动 | 持卡人 | POST `/campaigns`、`/activate` | 待鉴权落地后返回 403（POC 为已知缺口，D-10） |

## 11. 依赖与约束

### 11.1 依赖

| 依赖对象 | 用途 | 失败影响与处理 |
|---------|------|---------------|
| marketing-service | 活动配置、返现评估与记录 | 不可用时返现延迟，保留 `PENDING` 可重试；入账不受影响 |
| transaction-service | 入账后触发评估；消费类交易过滤（D-07） | 关闭 `MARKETING_ENABLED` 即停止评估，无返现 |
| account-service | 产品等级读取与返现贷记 | 读取失败导致评估失败；贷记失败保留 `PENDING` |
| reference-data-service | 交易类型/类别字典（`01` = Purchase） | 过滤规则按 `typeCode` 常量判定，字典不可用不影响过滤 |
| web-ui | 客户活动/返现页、运营活动页与代理 | 页面不可用时仅影响展示，不影响资金 |
| audit-service | 活动与资金操作留痕 | 写失败进入本地补偿日志 |

### 11.2 影响分析

| 维度 | 影响 |
|------|------|
| 前台 | 客户营销页展示额外返现活动与记录；运营活动创建表单默认值（费率 0.005、门槛 50.00、上限 30.00/300.00、预算 50 000.00、免报名） |
| 后台 | 配置侧：新增 1 条活动配置，无代码改动；代码侧：`transaction-service` 的 `PostingService.evaluateRewards` 增加消费类交易过滤（D-07） |
| 数据 | 新增 1 条 `campaign` 记录与对应 `reward_grant`、`account_credit` 记录，不改表结构 |
| 接口 | 复用现有活动、评估、奖励、效果接口，不新增接口 |
| 配置 | 费率 0.005、窗口 2026-11-13～2027-02-12、产品 `PLATINUM`、门槛 50.00、单笔上限 30.00、客户上限 300.00、预算 50 000.00、免报名 |
| 测试 | 费率与舍入、窗口边界、门槛边界、消费类过滤、幂等、上限与预算、贷记失败重试、多活动叠加 |
| 文档 | 本需求；运营活动配置说明；活动效果与对账口径 |

### 11.3 约束

- 返现只能经 account-service 贷记冲减欠款，营销库不直接改余额（ADR-013）。
- 金额统一 `BigDecimal` / `numeric(12,2)`，HALF_UP 2 位；费率取值 0–1。
- 不使用 MQ；本期为同步评估 + 幂等重试（ADR-009 方案 A、ADR-013 方案 B）。
- 现有鉴权缺口（ADR-007）不扩大：不得把营销接口暴露到公网（D-10）。
- 活动窗口按服务器时区（本地演示）；生产需统一业务时区（`docs/design/17` §8）。
- 既有白金卡 5% 活动配置不得在本需求内修改（D-01）。

## 12. 风险与假设

### 12.1 风险与应对

| 编号 | 风险/假设 | 影响 | 应对 |
|------|-----------|------|------|
| R-01 | D-01～D-10 由交付人授权决定，尚未经业务/财务/合规正式会签 | 会签若推翻口径（尤其 D-01、D-04），需重做计算与验收 | 两项口径均为活动配置，切换成本低；会签完成前不投产 |
| R-02 | 退款/拒付不回收返现（D-06） | 客户保留不应得返现的资金损失 | 业务与风控签认前控制预算规模；预留冲正设计 |
| R-03 | 预算/上限仅单实例保护 | 多实例部署下存在超发风险 | 演示单实例；多实例需行锁/条件更新（`docs/design/17` §8） |
| R-04 | 「未来 3 个月」按需求登记日起算（D-03） | 若业务要求自然月对齐，窗口需调整并重跑边界用例 | 窗口为活动配置项，调整后仅需重跑首末日用例 |
| R-05 | 活动配置变更无审批流程 | 误配置费率导致资金损失 | 活动创建/发布纳入运营双人复核（建议）；配置变更留痕 |
| R-06 | 无接口级鉴权（POC，D-10） | 未授权调用可改活动 | 仅环回地址/本地 Compose 暴露；生产前实施 ADR-007 方案 C |
| R-07 | 消费类过滤依据 `typeCode = "01"` 常量（D-07） | 若存在其他消费类类型编码，会漏发返现 | 开发节点核对 `GET /api/v1/transaction-types` 全量字典后确定过滤集合 |

### 12.2 假设

- 本需求不需要报名流程，`enrollmentRequired=false`（D-05）。
- 额外返现以独立活动形式落地，不影响既有活动的费率与上限（D-01）。
- 返现实时入账，不做日终批量。
- 仅消费类交易（`typeCode = "01"`）参与返现（D-07）。

### 12.3 残余待确认事项

| 编号 | 事项 | 责任方 | 是否需要阻断本次开发 | 状态 |
|------|------|--------|-------------------|------|
| RC-1 | D-01～D-10 的业务、财务、合规正式会签（含费率、窗口、门槛与上限额度、免报名、不回收返现） | 业务负责人 + 财务 + 合规 | 不阻断开发，阻断投产 | 待确认 |
| RC-2 | 退款、撤销、拒付的返现回收规则与冲正方式 | 业务 + 风控 | 不阻断本期开发（本期按 D-06 不回收） | 待确认 |
| RC-3 | 消费类交易的完整 `typeCode` 集合（是否存在 `01` 之外的消费类编码） | 开发 + 业务 | 阻断消费类过滤实现细节 | 待确认 |

## 13. 合规标注

| 维度 | 标注 |
|------|------|
| 监管（模拟） | 参照《商业银行信用卡业务监督管理办法》关于信用卡营销与客户知情的要求：返现规则须向客户明示，活动期限与上限须事先公示。本文件为演示材料，不构成监管合规结论。 |
| 制度（模拟） | 参照行内信用卡营销活动管理办法（模拟编号 MKT-POLICY-2026）：活动配置需审批、变更留痕、预算受控。本期口径由交付人授权决定，正式审批待 RC-1 会签。 |
| SoD（职责分离） | 活动创建与发布建议由不同角色执行；返现额只能由系统按规则计算，人工无直接改额权限；返现重试仅重放原金额。 |
| 隐私（模拟） | 参照《个人信息保护法》，仅处理返现必需的账户、交易与金额字段；日志不记录完整卡号与证件信息。 |
| 审计 | 活动配置变更、返现发放、贷记结果、重试操作全量留痕，留存 5 年（D-09）。 |
| 结论 | 模拟需求；费率、窗口、门槛、上限与预算额度为 D-01～D-10 决定值，投产前需业务、财务、合规三方会签（RC-1）。 |
