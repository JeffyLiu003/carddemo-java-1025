## 1. 实现正确性

| 检查项 | 结论 | 依据 |
|--------|------|------|
| 过滤位置（资金动作之后、下游调用之前） | 正确 | `PostingService`：过滤在 `evaluateRewards` 入口，此时 `balance`/`transaction`/`daily` 已落库；不改变入账结果 |
| 幂等与失败语义未变 | 正确 | 营销调用仍在 try/catch 内，失败只 WARN 不回滚（既有行为） |
| 配置解析 | 基本正确 | `split(",")` + `trim` + 丢弃空串 + `toUnmodifiableSet()`；空配置→空集合→等效关闭评估 |
| 大小写/格式容错 | 缺口（低） | 未做 `toUpperCase`；若配置写成 `purchase` 或含全角逗号将静默不匹配 |
| 可观测性 | 缺口（低） | 跳过非消费类交易时无 debug 日志/计数，线上排查「为什么没返现」只能靠推断 |
| 多处调用点覆盖 | 已核对 | `evaluateRewards` 仅由 `post(...)` 调用（单条与批量共用），无旁路 |

**主要风险**：默认值 `01` 是唯一放行的类型。若存在其它消费类编码（如网络/无卡/预授权完成），这些交易将**静默失去返现**，且无告警。PRD 已将此事列为 RC-3 待确认，配置化降低了修复成本，但上线前必须由业务确认类型集合。
